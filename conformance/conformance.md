# finlight API v3 conformance cases

Contract version 3.0.0-rc.4. Generated by `scripts/export-v3-contract` from the fixtures; do not edit by hand.

Every client runs every case below in its own test framework and keeps a table "case id → test name".
A case passes when the client behaves as the "Expected" column says, driven by the fixture file named in the case.

Names follow `docs/concepts/api-v3-client-rules.md` (R-NAMES-1) and the per-language table in
`docs/concepts/api-v3-sdk-style.md`. Error names are the base words: `FinlightApiError` for every error the API answers
(REST, refused WebSocket dials and terminal `connection.error` frames alike), with `apiKind` naming the kind
(`validation_failed`, `cursor_invalid`, `cursor_mismatch`, `unauthorized`, `forbidden`, `not_found`, `rate_limited`,
`internal_error`, `other`; languages with exception classes also have one subclass per kind, e.g. `NotFoundError`).
Local checks fail with `FinlightValidationError` before any request or dial. There is no separate dial error type.
A v2 webhook body is a `WrongPayloadVersion` result, never an error (Go alone reports it as `*webhook.WrongPayloadVersionError`).

## How to read the fixtures

- `fixtures/decode/*.json`: `wire` is the JSON the server sends; `expect.presence` gives, per key path, one of
  `absent` (key not in the JSON), `null`, `empty` (`[]`) or `value`. The client model must report the same state.
- `fixtures/forward-compat/*.json`: synthetic additions on top of real server output; `known` is the untouched part.
- `fixtures/requests/*.json`: `sdk` is the call, `request` the exact HTTP request (or `frame` the exact WebSocket
  message) the SDK must produce, `response` / `server.frames` what the server answered.
- `fixtures/pagination/*.json`: request/response pairs of a cursor walk; `rules` lists what the pager must do.
- `fixtures/errors/*.json`: `response` is the error as the server sends it; `expect.code` is the problem code
  (`NESTJS_FALLBACK`: no code, fallback form), `expect.apiKind` the error kind and `expect.retry` the retry class the
  client must derive (see `fixtures/errors/retry-classes.json`).
- `fixtures/webhook/*.json`: `secret`, the received `request` (headers and raw body; `rawBodyBase64` holds the exact
  bytes), the verification clock `verify.now` with `verify.toleranceSeconds`, and the expected outcome: `event`
  (a `WebhookEvent`), `wrongPayloadVersion` (a `WrongPayloadVersion` result, not an error) or `error`
  (`WebhookVerificationError` with its `reason`).
- `ws-sessions/*.json`: optional `clientConfig` (stream settings the case needs, by base word), then ordered `steps`:
  `dial`, `clientSends` (exact `frame` or a `match` subset), `serverSends`, `serverCloses`, `advance` (fake clock, ms)
  and `expect` (`outcome` is one of admitted, item, liveness, logOnly, reported, duplicateDropped, noAdmitted,
  terminalError, reconnect, noReconnect). `reported` means: passed to the named hook (fields are those of its info object), the stream keeps running.
  `terminalError.error` is `FinlightApiError` (with `apiKind`) or `PreemptedError`.

Fixtures marked `"synthetic": true` were not produced by server code; everything else was generated from the server
code. All article text, companies, tickers, ISINs, keys and secrets in the kit are synthetic.
